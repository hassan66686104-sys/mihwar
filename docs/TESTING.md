## أين تعمل الاختبارات؟ (بصراحة)

### `test:db`

تعمل على PostgreSQL 16 محلي، مع ملف بسيط يحاكي أدوار Supabase (`tests/db/supabase-stub.sql`). تطبّق ملفات `supabase/migrations/` نفسها مرتين لتثبت أنها قابلة لإعادة التشغيل. بعدها تستدعي الدوال بأدوار `anon` و`authenticated` كما تفعل PostgREST.

### `test:e2e`

تعمل على بيئة محلية يشغّلها `scripts/e2e-stack/start.mjs`، وفيها:

- PostgreSQL محلي مع الـ migrations نفسها.
- **PostgREST 12 الحقيقي**، وهو المحرك نفسه خلف `/rest/v1` في Supabase.
- **Supabase Auth (GoTrue) v2.197 الحقيقي** لإنشاء حساب المعلم وتسجيل دخوله.
- بوابة صغيرة على المنفذ 54321 **تحاكي** قناة Realtime (بروتوكول Phoenix للبث فقط). **ليست** خادم Supabase Realtime الحقيقي.

### ما لم يُختبر

- **التدفق الكامل على مشروع Supabase السحابي:** بيئة التطوير لا تستطيع الوصول إلى `supabase.co`. على المشروع السحابي تحقّقنا عبر SQL مما يلي فقط:
  - وجود الجداول والدوال.
  - RLS مفعّل على كل الجداول، و21 سياسة قراءة.
  - الزائر لا يقرأ الجداول، ولا ينفّذ دوال المعلم أو الدوال الداخلية.
  - عمود `token_hash` محجوب عن المعلم.
- **خادم Supabase Realtime الحقيقي.**
- **الحمل:** عشرات الطلاب في الوقت نفسه.

### تشغيل اختبارات المتصفح

```bash
# يتطلب: PostgreSQL محلي، وملفي postgrest و supabase/auth في مجلد (STACK_BIN)
STACK_BIN=~/.stack node scripts/e2e-stack/start.mjs &   # يكتب .env.e2e
npm run test:e2e                                         # يشغّل vite --mode e2e تلقائيًا
```
